Design walkthrough

A GUI between the researcher and the optimizer

Specify property targets in a form → launch single-point or Pareto runs → browse the resulting space of designs.

  • The optimizer today: two CLI scripts with ~40 property-target flags, or a chat-only compogen plugin.
  • The gap: no form-based GUI, dashboard, or HTTP API anywhere in the repo.
  • The build: a structured input form, live progress, and an interactive results view — no CLI flags to memorize.
  • Reuse, don't rebuild: the optimizer stays exactly as it is — the GUI builds its command line, reads its artifacts, and changes nothing upstream.
Component 1

Architecture & data flow

One execution layer (the Runner) sits between the form and the optimizer; artifacts feed the results view and a run store.

  • Form → RunConfig: a validated object written from scratch against the argparse surface — there is no Pydantic schema upstream to reuse.
  • Runner: the single seam — submit / stream / result / cancel.
  • Optimizer unchanged: the same IPOPT + Allen–Cahn stack writes the same .npz/.png artifacts.
  • Results view reads artifacts; run store persists every run for history & compare.
  • Live events stream back through the Runner during a solve, via a line classifier and a pure reducer that can replay a log from disk.
  • Also built, not drawn: a preflight doctor, a re-runnable run.sh per run, a solve-count estimate that gates Launch, and reattach to a run that outlived the browser session.

Component 3

Input form — sections A–F

A thin editor over the existing TuningConfig / PhaseProps schema and the directive grammar.

  • Active-physics gating: only relevant properties appear; isotropic by default with a per-component toggle for the anisotropic set.
  • No plasticity: neither entry point has a plasticity checkpoint, directive, or flag, so section A offers three families, not four.
  • Directives → optimizer: max/min become objective terms, target/range become hard constraints.
  • Phase props seed from explicit values, a consolidated HDF5, or built-in defaults.
  • Validation is per-field and non-blocking where it can be: errors disable Launch, warnings explain the upstream behaviour instead of guessing for you.
Component 4

Two optimizers, one mode switch

A top-level toggle re-renders the targets, tuning, and results view; everything else is shared.

  • Single-point (run_inverse_design_fm_multi_ac.py): one design; supports weights, VF bounds, and multiple restarts.
  • Pareto (run_pareto_epsilon_fm_multi_ac.py): ρ as primary objective, other targets swept as ε-constraints.
  • Different defaults surfaced in the form (e.g. target_tol, restarts).
  • The ε grid is a Cartesian product, so the form estimates the solve count and makes you acknowledge a sweep past a threshold. --dry_run prints the estimate without solving.
  • Shared: physics, phase props, and validation sections.
Component 5 · decided subprocess

Execution model — the Runner interface

One interface, one shipped backend. The other two turned out not to be drop-in replacements.

  • Subprocess — built. Builds argv for either script; zero optimizer changes; covers both modes. Spawns the solver env's interpreter directly, never conda run, which builds a 4-deep tree that survives terminate(); cancel is killpg on the run's own process group.
  • In-process — foreclosed, not deferred. It would make the GUI process be the solver env, and cancel() is unimplementable: you cannot interrupt a thread inside C++ IPOPT.
  • compogen — a later integration, not a backend you configure. Staging and cluster scale are real; the logbook is not, and its 20-tool registry is strictly forward simulation with no inverse-design or Pareto tool. It depends on compgen (MOOSE/Sculpt), not on ai4ns.
  • So "interchangeable" was wrong. The seam is still worth having — it is what makes the GUI testable against a stand-in optimizer — but the choice is environmental, not a config flag.
Component 6 · centerpiece

Design-space view — click reveals the mask

Every candidate design is a point in property space; clicking one shows its microstructure and how well it meets the criteria.

Pareto front (rank 0) dominated target
  • Points: Pareto solutions (colored by rank, feasibility) or single-point restarts, from the run's .npz.
  • Axis pickers: choose any two effective properties (E vs ρ, κ vs α, …), with the requested target drawn as a band.
  • Click, not hover. Plotly hover events do not round-trip to Python in Streamlit; selection does. The tooltip still carries the numbers, so hovering stays informative and the click opens the detail.
  • Detail: the 128×128 binary mask, achieved-vs-target with per-criterion ✓/✗ and fractional error, convergence curve, and the FEniCS column when validation ran.
  • Selection reads customdata, never the point index: points are split across traces so the legend can filter them, and a trace-relative index would open a different design's microstructure.
Component 7

Live progress + logs

Watch the solve as it happens; points populate the design space as they are produced.

  • Read stdout through a PTY, not a pipe. The iteration table is written by IPOPT's C++ Journalist to C-level stdout, where python -u has no effect; against a pipe glibc block-buffers it and all the rows arrive at once, on exit.
  • Progress indicator: single-point shows iterations; Pareto shows explicit stages 0–3 and grid position.
  • Sweep coverage, not incremental points: how many grid points have reported and how many found a feasible restart, so a barren sweep is visible while there is still time to cancel.
  • Designs cannot stream in. Both scripts write their .npz after the solve, and the sweep never prints an achieved property vector per grid point — only ε targets, restart status, and a feasible count. Live points would need an upstream change.
  • The log is the source of truth: a pure reducer replays it from disk, so a reattached run rebuilds its progress exactly.
Component 8

FEniCS / MOOSE validation

Optional ground-truth PDE check, shown beside the surrogate prediction in the detail panel.

  • Toggle in section F; per-phase fenics_* props or an H5 source, plus the conda env name.
  • Reads the run's own results: fenics_<physics>_results.npz per physics, homogenised with upstream's exact maths so the panel agrees with the CLI's table. Written inside the run directory, so two runs never overwrite each other's ground truth.
  • Side-by-side NN vs FEniCS per property, with the surrogate's error against the PDE alongside its error against the target — a design can hit its target and still be wrong.
  • Not skipped gracefully — the reason the toggle is gated. Upstream calls the validator with no try/except, after the solve and before artifacts are written, so a broken env destroys a completed run.
  • Three defences: default off; conda injected into the child's PATH; and a preflight that imports the validator inside the env rather than checking the env exists. Existence is not usability — the upstream environment_fenics.yml omits dolfinx_mpc and pandas, so a by-the-book env passes a name check and dies at import.
Component 9

Run history & compare

Every run is persisted; reload a run into the plot, or compare designs across runs.

  • Persist: config JSON, argv, status, log, artifacts and a re-runnable run.sh per run — the same record the Runner uses to reattach after a restart.
  • Not compogen's logbook: read_design_logbook / annotate_last_run do not exist. The run store is ours, and it had to exist anyway.
  • Reload: a past run drops back into the design-space plot.
  • Compare: pin up to four designs from any runs — masks side by side, a property table with the relative spread called out, and a convergence overlay padded with NaN so an early-converging run stops being drawn instead of flatlining.
Component 10 · decided streamlit

Framework choice & the three decisions

Shipped as a form-first Streamlit GUI. The chat entry point was not built, and no longer looks like the same project.

  • Interactive selection rules out static matplotlib — Streamlit + Plotly, with the click caveat from Component 6.
  • Decision 1 — framework: Streamlit, single surface. Chainlit is not built. A chat front-end would share the Runner, but it is a second product, not a second view.
  • Decision 2 — execution: subprocess. Not merely "v1" — in-process is foreclosed by the environment split and by cancel(), so this is the design, not a starting point.
  • Decision 3 — Pareto via compogen: deferred. compogen has no coupling to ai4ns and no inverse-design tool; the barrier is dependency resolution (ai4ns pins ~292 packages exactly), not a missing @tool.
  • Still open: whether to patch upstream so designs can stream into the plot during a sweep — the only deck promise that needs a change on the optimizer's side.
