Design walkthrough

A GUI between the researcher and the optimizer

Specify property targets in a form → launch single-point or Pareto runs → browse the resulting space of designs.

  • The optimizer today: two CLI scripts with ~40 property-target flags, or a chat-only compogen plugin.
  • The gap: no form-based GUI, dashboard, or HTTP API anywhere in the repo.
  • The build: a structured input form, live progress, and an interactive results view — no CLI flags to memorize.
  • Reuse, don't rebuild: the input schema and the optimizer stay exactly as they are.
Component 1

Architecture & data flow

One execution layer (the Runner) sits between the form and the optimizer; artifacts feed the results view and a run store.

  • Form → RunConfig: a validated object built from the existing Pydantic schema.
  • Runner: the single seam — submit / stream / result / cancel.
  • Optimizer unchanged: the same IPOPT + Allen–Cahn stack writes the same .npz/.png artifacts.
  • Results view reads artifacts; run store persists every run for history & compare.
  • Live events stream back through the Runner during a solve.
Component 2

Three-pane layout

Input · Run/progress · Design-space, with a run-history strip along the bottom.

Component 3

Input form — sections A–F

A thin editor over the existing TuningConfig / PhaseProps schema and the directive grammar.

  • Active-physics gating: only relevant properties appear; isotropic aliases by default, anisotropic + sigY_* behind an "advanced" expander.
  • Directives → optimizer: max/min become objective terms, target/range become hard constraints.
  • Phase props seed from explicit values, a consolidated HDF5, or built-in defaults.
  • Reuse: fields, labels, and typical ranges come straight from TuningConfig.
Component 4

Two optimizers, one mode switch

A top-level toggle re-renders the targets, tuning, and results view; everything else is shared.

  • Single-point (run_inverse_design_fm_multi_ac.py): one design; supports weights, VF bounds, and plasticity.
  • Pareto (run_pareto_epsilon_fm_multi_ac.py): ρ as primary objective, other targets swept as ε-constraints; excludes plasticity.
  • Different defaults surfaced in the form (e.g. target_tol, restarts).
  • Shared: physics, phase props, and validation sections.
Component 5 · open decision execution

Execution model — the Runner interface

One interface, interchangeable backends, so the execution choice is not baked in.

  • Subprocess (recommended v1): builds argv for either script; zero optimizer changes; covers both modes today.
  • In-process: imports utils.optimization for structured per-iteration progress; tighter coupling.
  • compogen HPC/MCP: reuses staging, logbook, and cluster scale — needs a new Pareto @tool for parity.
  • Same schema & artifacts across all three — the GUI code doesn't change when the backend does.
Component 6 · centerpiece

Design-space view — hover reveals the mask

Every candidate design is a point in property space; hovering shows its microstructure and how well it meets the criteria.

Pareto front (rank 0) dominated target
  • Points: Pareto solutions (colored by rank, feasibility) or single-point restarts, from the run's .npz.
  • Axis pickers: choose any two effective properties (E vs ρ, κ vs α, …).
  • Hover → popover: the 128×128 binary mask + a per-criterion ✓/✗ with fractional error.
  • Click → detail: full mask, achieved-vs-target table, convergence curve, validation.
  • Needs an interactive chart (Plotly/Bokeh) — not the CLI's static PNG.
Component 7

Live progress + logs

Watch the solve as it happens; points populate the design space as they are produced.

  • Subprocess backend: tail stdout — IPOPT prints per-iteration status (verbosity via ipopt_print).
  • In-process / compogen: forward structured events instead of parsing text.
  • Progress indicator: single-point shows iterations; Pareto shows explicit stages 0–3.
  • Incremental plot: designs appear in the scatter as each restart / grid-point finishes.
Component 8

FEniCS / MOOSE validation

Optional ground-truth PDE check, shown beside the surrogate prediction in the detail panel.

  • Toggle in section F; per-phase fenics_* props or an H5 source, plus the conda env name.
  • Reads existing artifacts: single-point fenics_*_results.npz / the CLI's third PNG panel; compogen path uses the MOOSE table.
  • Side-by-side NN vs ground-truth with per-property error.
  • Graceful fallback: a clear "validation unavailable" notice when the solver is missing.
Component 9

Run history & compare

Every run is persisted; reload a run into the plot, or compare designs across runs.

  • Persist: config JSON + artifact paths + status + achieved props + timestamp in a runs directory.
  • Or reuse compogen's markdown logbook via read_design_logbook / annotate_last_run.
  • Reload: a past run drops back into the design-space plot.
  • Compare: pin designs from multiple runs — masks side-by-side, tables, convergence overlay.
Component 10 · open decision framework

Framework choice & open decisions

Recommendation: a form-first Streamlit GUI plus a Chainlit chat entry point sharing one Runner.

  • Interactive hover rules out static matplotlib — favors Streamlit/Gradio/web; Chainlit needs a custom element.
  • Not a fork: both surfaces share the Runner and input schema.
  • Open 1 — framework: Streamlit + Chainlit, or a single surface?
  • Open 2 — execution default: Subprocess (v1) or start from compogen/HPC?
  • Open 3 — Pareto via compogen: new pareto_epsilon_composite tool in v1, or defer?
